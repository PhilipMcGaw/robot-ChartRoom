Maker's Pet's 120 mm Arduino/ROS 2 Self-Driving Robot Build Pack and its companion e-book, **Build, Program a Self-Driving Robot** (edition 1.0, 209 pages, published 2026-11-08), are useful references for small differential-drive robotics, encoder-based odometry, low-cost LiDAR, ROS 2 integration, simulation, and staged educational bring-up.

The material is primarily relevant to **SwarmBot and MarsBot**, and parts of the control and simulation approach may inform K9, PiWars, and the wider Robots learning material. It is a terrestrial indoor robot; it is not a hardware target for the underwater ROV.

===== Platform and architecture =====

The documented 120 mm robot combines:

  * two N20 geared DC motors with quadrature encoders, arranged as a differential drive;
  * an ESP32 development board, programmed using the Arduino IDE;
  * a BDC-30P motor-driver board;
  * an LDROBOT LD14P 2D scanning LiDAR;
  * a small 3D-printed chassis and separately printable mechanical parts; and
  * a PC running ROS 2, connected to the robot over 2.4 GHz Wi-Fi.

The ESP32 handles low-level motor and sensor interfaces. The PC runs the higher-level ROS 2 functions: visualisation, mapping, localisation, navigation, and user programs. The book describes a Micro-ROS connection between the ESP32 and the ROS 2 environment. The PC is therefore the computational host; the robot is not a self-contained ROS 2 computer.

The documented software baseline is Kaia.ai firmware 0.8.0 for ROS 2 Iron, ESP32 Arduino board package 2.0.17, and the `kaiaai/kaiaai:iron` Docker image. A Jazzy image is also documented. The book's Ubuntu path uses Ubuntu 22.04 for Iron; its Jazzy references use Ubuntu 24.04. Treat these as the book's tested/documented baseline, not as a recommendation to replace the Robots project's existing ROS 2 Jazzy environment.

===== Main technical content =====

==== 1. Differential drive, motor control, and odometry ====

The robot uses two encoder-equipped drive motors. The firmware exposes motor speed and encoder parameters, including encoder pulses per revolution (PPR), wheel diameter, wheel track, and maximum motor RPM.

The troubleshooting material is particularly useful: it explains that an incorrect encoder PPR value can cause odometry drift, map distortion, or the robot appearing to drive off the map. In this implementation, the firmware multiplies the configured 1× encoder PPR by four to account for quadrature edges. The author recommends counting ticks over one complete wheel revolution and entering the corresponding 1× value.

This is relevant to the Robots project's preference for **closed-loop wheel-velocity control using encoder feedback**, with higher-level navigation issuing wheel-speed targets. It is a useful practical reference for:
  * separating commanded wheel speed from measured wheel speed;
  * calibrating encoder resolution and wheel geometry;
  * checking left/right motor symmetry;
  * understanding the effect of odometry errors on mapping; and
  * diagnosing whether an apparent SLAM problem is actually a drivetrain calibration problem.

Do not copy the Maker's Pet PPR, wheel diameter, wheel track, or RPM values into another robot. They are specific to its motors, encoders, wheels, and firmware configuration.

==== 2. LiDAR, coordinate frames, and mapping ====

The guide uses a 360° 2D LiDAR for scan visualisation and mapping. It documents a useful diagnostic sequence: confirm that the sensor spins, check that the ESP32 receives scan data, and then verify that the data reaches ROS 2 and is visible in RViz.

It also identifies several practical LiDAR limitations. A planar scanner can miss objects that are black or non-reflective, transparent, below or above its scan plane, very thin, highly reflective, or affected by strong near-infrared illumination. These are sensor-physics and installation constraints, not simply navigation-software defects.

A particularly useful distinction is made between:
  * **odometry calibration errors**, which can distort the map as the robot moves; and
  * **LiDAR-to-URDF frame alignment errors**, which can make a scan or map appear to slide sideways when the robot travels straight.

The guide recommends checking the LiDAR yaw offset in the robot description when the scan is rotated relative to its configured frame. This is a useful example of why coordinate-frame definitions and physical sensor mounting must agree.

==== 3. SLAM, Nav2, and autonomous exploration ====

The documented workflow progresses from manual teleoperation to mapping and autonomous navigation:

  * view the live LiDAR scan in RViz;
  * drive manually while SLAM builds a map;
  * save the occupancy map;
  * navigate to a selected goal using Nav2; and
  * use frontier exploration to explore and map unknown areas.

The quick-reference appendix includes commands for the Kaia.ai bring-up, teleoperation, mapping, map saving, and navigation. These are implementation-specific commands, but the workflow is useful as a learning sequence.

The troubleshooting section also connects navigation failures to practical constraints: narrow passages, clutter, poor maps, unsuitable LiDAR geometry, incorrect robot dimensions, and insufficient PC processing performance. It discusses Nav2 parameters such as forward velocity, angular velocity, acceleration limits, and obstacle inflation radius. These values are examples for the Maker's Pet robot, not portable tuning values.

==== 4. Gazebo and Software-in-the-Loop ====

The simulation chapter is one of the strongest reasons to retain this resource. It runs a simulated version of the robot in Gazebo, with a simulated LiDAR, and uses the ROS 2 mapping and navigation stack to drive, map, and navigate a virtual environment.

The same broad application workflow can therefore be explored before purchasing or assembling the physical kit. The guide also describes running user programs against the simulated robot.

This is directly relevant to the Robots project's **Software-in-the-Loop (SiL) and Hardware-in-the-Loop (HIL)** learning and test strategy:
  * establish the robot description and sensor model;
  * verify teleoperation and velocity command paths;
  * exercise mapping and navigation in simulation;
  * compare simulated and physical odometry/sensor behaviour; and
  * make the transition to physical hardware an explicit integration and validation step.

The existence of a working simulation does not by itself validate the physical robot, its sensor model, or its control performance. Any transfer of this workflow to SquidLink should use the project's own ROS 2 Jazzy workspace and simulation authority.

==== 5. Embedded/host communications and multiple robots ====

The documented architecture uses Wi-Fi to connect the ESP32 to the PC-hosted ROS 2 environment. The ESP32 supports 2.4 GHz Wi-Fi, not 5 GHz. The guide identifies packet loss and unreliable Wi-Fi as causes of missing telemetry or LiDAR data.

For running more than one robot from one PC, the guide suggests one Docker container per robot and a distinct host UDP port for each instance. It also discusses ROS 2 topic namespacing through configuration changes.

This is a useful worked example of multi-robot bring-up and isolation, particularly for SwarmBot experiments. It is **not** the Robots project's communications architecture: Chartroom's current project boundary uses NATS for the wider system, and the Maker's Pet arrangement should not be adopted as a substitute for the project's NATS interfaces or ROS 2 bridge. It is worth studying as a contained robot-to-host transport example.

==== 6. Programming and staged learning ====

The book includes example Python programs, including object-facing and person-following behaviours, and shows how to extend the robot software. The overall learning progression is useful:

  1. assemble and inspect the hardware;
  2. establish firmware and communications;
  3. verify each motor, encoder, and sensor;
  4. teleoperate the robot;
  5. map an environment;
  6. add localisation and navigation;
  7. run autonomous exploration; and
  8. write higher-level behaviours.

This is a good template for modular educational exercises. The physical robot and the Kaia.ai software are examples, not prerequisites for adopting the progression.

===== Relevance to Robots projects =====

==== SwarmBot ====

A strong reference for compact differential-drive hardware, low-cost sensing, staged bring-up, and introductory autonomy. The multi-robot Docker/UDP example is worth examining as a practical deployment pattern, while retaining the project's own communications and control boundaries. LiDAR should remain an optional advanced module rather than a requirement for every educational robot.

==== MarsBot ====

A useful small-scale terrestrial reference for differential-drive kinematics, encoder calibration, 2D LiDAR mounting, SLAM, Nav2, frontier exploration, and simulation-first development. MarsBot should not copy the 120 mm chassis; the value is in the algorithms, interfaces, and staged test approach.

==== K9 and PiWars ====

The encoder and closed-loop speed-control material supports the existing requirement for wheel-velocity feedback on K9. The navigation and simulation chapters may also be useful for PiWars, subject to the competition robot's actual sensors, processing platform, and operating environment. The Maker's Pet hardware is not a direct hardware recommendation for either robot.

==== ROV and SquidLink ====

The terrestrial 2D LiDAR chassis is not directly applicable to underwater navigation. The transferable material is the ROS 2/Gazebo workflow, differential-drive modelling, sensor-frame discipline, odometry calibration, and the distinction between simulated and physical validation. SquidLink remains authoritative for the project's ROS 2 and Gazebo implementation.

===== Critical review and limitations =====

  * **Version age and compatibility:** the e-book's primary baseline is ROS 2 Iron and older ESP32 Arduino tooling. It mentions a Jazzy image, but project use should be checked against current ROS 2 Jazzy and Ubuntu 24.04 dependencies.
  * **Hardware specificity:** wiring, pin assignments, encoder PPR, motor limits, LiDAR model settings, and Nav2 tuning are specific to the Maker's Pet boards and chassis.
  * **Network dependency:** the robot depends on a stable 2.4 GHz Wi-Fi link to the host. Packet loss can affect telemetry and scan delivery.
  * **Simulation fidelity:** Gazebo is valuable for software development, but physical drivetrain, sensor, Wi-Fi, and timing effects still require separate tests.
  * **LiDAR coverage:** a single planar scanner does not detect every obstacle or object geometry.
  * **No automatic project adoption:** the guide is a learning/reference source. It does not establish a design decision, selected component, or validated capability in any Robots project.

===== Suggested reading order =====

For the most transferable material, prioritise:
  1. Chapter 3 — firmware upload and physical bring-up, for the sequence of low-level checks.
  2. Chapter 4 — manual mapping, for teleoperation, odometry, and frame alignment.
  3. Chapter 5 — autonomous exploration and navigation, for SLAM, Nav2, and frontier exploration.
  4. Chapter 6 — simulation, for the Gazebo workflow.
  5. Appendix B — troubleshooting, particularly encoder calibration, LiDAR diagnostics, Wi-Fi packet loss, and map distortion.
  6. Appendix C — command reference, as a quick index to the implementation-specific commands.

===== Status =====

**Status:** Research / learning reference. Not a selected hardware platform, adopted software dependency, or validated Robots project design.

**Review basis:** Maker's Pet's e-book announcement and product documentation, plus the published Markdown source chapters and authoring instructions in the Maker's Pet e-book repository. A copy of the publisher PDF supplied for Chartroom is retained in media for reference.

**Further work:** If this material is used for a hands-on ROS 2 exercise, reproduce the concepts in the project's Jazzy/SquidLink environment and record any differences. Keep any project-specific implementation and test results in the authoritative repository.
