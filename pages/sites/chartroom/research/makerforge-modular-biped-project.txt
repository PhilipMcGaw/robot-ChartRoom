===== Project overview =====

MakerForge's site describes a modular biped robot project with Raspberry Pi and Arduino-based builds, custom printed circuit boards, 3D-printed parts, servos, sensors, and camera/audio features. The public project repository provides code and a project wiki with build information and a bill of materials.

The site presents three generations: Archie as the original legacy build, Buddy as the current stable build, and Cody as a preview using a custom Raspberry Pi Compute Module 5 carrier board. These are the project's own release descriptions, not Chartroom assessments of reliability.

===== Status and evidence =====

The project's GitHub wiki, edited 2026-02-26, describes Buddy as the current release but states that it can perform movements and poses and is not yet capable of walking. This gives a more specific capability boundary than the site's general description of Buddy as stable. Walking should therefore be treated as unimplemented in the cited wiki snapshot; check the current repository before relying on later progress.

The project may be useful as an educational reference for modular companion-robot construction, Raspberry Pi/Arduino division of work, servo control, and custom printed circuit boards. It is a separate biped platform and does not establish compatibility with, or adoption in, the Robots project's vehicle architecture.

===== Dependency-management article =====

MakerForge's article on [dynamic dependency management](https://www.makerforge.tech/posts/dynamic-dependency-management/) describes listing Python and system-package dependencies in each module's YAML configuration, then having an installation script install dependencies for enabled modules. This pattern can help when optional modules have different requirements and deployments enable different feature sets.

The article's example is not, by itself, a reproducible dependency solution: its Python and system package installation examples do not consistently pin versions or use a lock file, and the virtual environment is created with system packages visible. It also uses broad `chmod 777` permissions for startup scripts. These are limitations of the published example, not a review of the current MakerForge repository.

Chartroom's [[sites:chartroom:development:raspberry-pi-deployment|Raspberry Pi deployment guidance]] assigns implementation-specific dependency installation to CuttleOS. This article is a useful design reference if CuttleOS needs per-module or per-profile dependency selection; the available Chartroom material does not establish that this added mechanism is currently needed or adopted. Any evaluation belongs in CuttleOS and should preserve repeatable versions, isolated environments, and least-privilege file permissions.
